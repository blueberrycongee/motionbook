# Interaction specification

Use inline for a small explanation or adaptation. Record decisions needed for the task, not a mandatory report of every field:

- **Need:** user goal, current state, uncertainty or desired expressive effect, and target component/runtime
- **Mechanism:** trigger or state → perceptible cue/control → intended understanding, action or experience. Separate observed source behavior from an untested benefit
- **Transfer:** the smallest useful behavior or relationship; which visual choices carry its value, which can change, and when a simpler or static treatment would suffice
- **State flow:** start, trigger, transition, result, cancellation and reversal
- **Constraints:** real data/latency, input, layout, repetition and failure cost; keyboard, touch, focus and reduced-motion equivalents
- **Motion:** anchors, layout relationships and consequential timing/easing values, linked to source; mark estimates and target adaptations
- **Checks:** starting condition, action and expected state/feedback. Test the intended role, not just resemblance

For example, a shared cover during player expansion can help identify the same media across two layouts: preserve that identity and reversible transition, not the demo's cover art or fixed coordinates. This is a rationale to evaluate, not measured evidence that users stay oriented.

A starfield may serve a requested sense of depth or wonder. Keep it only if it supports that expressive goal within legibility, motion and performance constraints; do not claim it improves navigation. A static treatment may carry the same value.

Choose failure paths that matter: interrupted expansion, cancelled dragging, repeated pending submission, errors/retry, long content and narrow layouts. For explanations, state which checks remain unrun; for integrations, execute them and report observed results or blockers.
